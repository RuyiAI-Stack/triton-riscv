# Inspecting Intermediate Representations

> **Audience:** Kernel Developers and Compiler Contributors. Beginners do not
> need IR dumps to complete the first example.
>
> **Prerequisites:** a working environment and a successful strict Host CPU
> vector-add run from the
> [Quick Start](00-Getting-Started.md#15-minute-quick-start).
>
> **Outcome:** produce the five vector-add IR files, understand what each file
> represents, and identify the first compiler stage containing a problem.

IR dumps are the most useful way to answer “which compiler stage introduced
this failure?” This guide follows the same `test_vec_add.py` kernel used in the
Quick Start. It runs through the **Host CPU** backend; dumping these files does
not create or execute a RISC-V ELF.

## Create an Isolated Vector-Add Dump

After activating the build environment, choose a dump directory and a fresh
kernel cache:

```sh
export TRITON_SHARED_DUMP_PATH="$PWD/artifacts/ir/vec-add"
export TRITON_CACHE_DIR="$PWD/artifacts/cache/vec-add-ir"
rm -rf "$TRITON_SHARED_DUMP_PATH" "$TRITON_CACHE_DIR"

python -m pytest python/examples/test_vec_add.py -v -s
find "$TRITON_SHARED_DUMP_PATH" -maxdepth 1 -type f -print | sort
```

Success means pytest finishes with `PASSED` and the listing contains:

```text
.../ll.ir
.../ll.mlir
.../tt.mlir
.../ttshared.mlir
.../vector.mlir
```

The test prints its maximum difference but does not assert it. Run the strict
Quick Start check first so this document can focus on compiler representations.

Why set a fresh cache? Triton does not rerun the compiler pipeline when it can
reuse a compiled kernel. A successful test with an empty dump directory often
means the object came from cache.

Why run one test? Dump filenames are stage names rather than per-kernel names.
A process that compiles several kernels can overwrite an earlier kernel's
files. Use a different directory for each reproducer.

The source-build environment helper sets a default dump directory under
`~/.triton/dump/shared`, but an explicit per-test directory is easier to reason
about.

## Files and Stages

A normal default-pipeline compilation produces:

```text
tt.mlir
ttshared.mlir
vector.mlir
ll.mlir
ll.ir
```

| File | What it contains | First questions to ask |
| --- | --- | --- |
| `tt.mlir` | TTIR after Triton's initial passes | Does the frontend express the kernel and pointers as expected? |
| `ttshared.mlir` | output of Triton-RISCV's structured conversion | Are shapes, strides, masks, and Linalg operations correct? |
| `vector.mlir` | output of Buddy's vector-oriented lowering | Did operations vectorize, and are extra allocations/copies visible? |
| `ll.mlir` | LLVM-dialect MLIR before translation | Did all high-level dialects lower legally? |
| `ll.ir` | textual LLVM IR passed to object generation | Is the ABI, target-independent control flow, and memory code correct? |

In plain language:

- **TTIR** is Triton's first compiler form for the specialized Python kernel.
- **Linalg** expresses structured computation; **MemRef** expresses shaped
  memory views with offsets and strides. Both can appear in `ttshared.mlir`.
- the **Vector Dialect** makes portable vector operations explicit in
  `vector.mlir`.
- **LLVM IR** is low-level code consumed by LLVM before an object file is
  emitted.

The optional IME path can omit `vector.mlir` because it uses a different Buddy
pipeline. Object bytes are not copied by this dump helper. For RISC-V machine
instructions, generate or disassemble an ELF as described in
[RISC-V ELF and QEMU](06-RISCV-QEMU.md#inspect-the-elf-and-assembly).

## Read the Files in Order

Do not begin with LLVM IR unless the failure is already known to be in code
generation. Follow one operation through the stages.

For vector addition, useful searches are:

```sh
rg -n "tt\.(load|store|addptr)|arith\.addf" \
  "$TRITON_SHARED_DUMP_PATH/tt.mlir"

rg -n "linalg|memref|bufferization|alloc|copy|materialize" \
  "$TRITON_SHARED_DUMP_PATH/ttshared.mlir"

rg -n "vector\.|alloc|copy|scf\.|affine\." \
  "$TRITON_SHARED_DUMP_PATH/vector.mlir"

rg -n "llvm\.|unrealized_conversion_cast" \
  "$TRITON_SHARED_DUMP_PATH/ll.mlir"

rg -n "define|load|store|call.*(malloc|free)" \
  "$TRITON_SHARED_DUMP_PATH/ll.ir"
```

Track data flow, not SSA names. Names such as `%7` are unstable after
canonicalization. Shapes, types, offsets, strides, operation kinds, and the
relationship between a load, computation, and store are more meaningful.

## What Healthy Lowering Looks Like

For a regular elementwise kernel, expect these broad changes:

```text
TTIR
  tt.load + arith + tt.store

Structured IR
  explicit memory views + tensor/Linalg computation + destination

Vector IR
  vector/scalar loads + vector arithmetic + stores or loops

LLVM IR
  ordinary pointer arithmetic, loads, arithmetic, stores, and launch ABI
```

Common warning signs include:

- a base pointer or branch-local offset disappears after `tt.mlir`;
- a mask becomes an unconditional access without a proven bound;
- `builtin.unrealized_conversion_cast` survives into `ll.mlir`;
- a simple elementwise kernel gains `memref.alloc`/`memref.copy` or
  `malloc`/`free` unexpectedly;
- the output view has a different shape or stride from the intended store;
- LLVM IR exposes the wrong argument type or omits launch-grid arguments.

An allocation is not automatically a correctness bug. It may be a conservative
bufferization result. Treat it as an optimization issue only after proving that
aliasing, masking, and non-contiguous access semantics permit direct use.

## Run a Pass Without the Python JIT

Use `triton-shared-opt` when you already have a small TTIR/MLIR reproducer:

```sh
"$TRITON_SHARED_OPT_PATH" input.mlir \
  --triton-to-linalg-experimental=structured-ldst-mode=tensor-first-vector-cpu \
  --mlir-print-debuginfo \
  -o output.mlir
```

This isolates the Triton-RISCV middle layer from:

- Python AST and specialization behavior;
- Buddy's vector/LLVM passes;
- object generation;
- the host launcher or QEMU runner.

To see the available project passes and options:

```sh
"$TRITON_SHARED_OPT_PATH" --help | less
```

Focused inputs under `test/Conversion/` are good templates for writing a
minimal reproducer. Keep only the operation, pointer pattern, mask, and control
flow needed to trigger the behavior.

## Compare Before and After a Change

Use separate cache and dump directories for the two revisions:

```sh
export TRITON_SHARED_DUMP_PATH="$PWD/artifacts/ir/before"
export TRITON_CACHE_DIR="$PWD/artifacts/cache/before"
python -m pytest python/examples/test_vec_add.py -v

# Rebuild after editing, then use new directories.
scripts/rebuild-triton-riscv.sh
export TRITON_SHARED_DUMP_PATH="$PWD/artifacts/ir/after"
export TRITON_CACHE_DIR="$PWD/artifacts/cache/after"
python -m pytest python/examples/test_vec_add.py -v

diff -u artifacts/ir/before/ttshared.mlir artifacts/ir/after/ttshared.mlir
diff -u artifacts/ir/before/vector.mlir artifacts/ir/after/vector.mlir
```

Compiler diffs contain harmless renumbering and formatting changes. A good
regression test checks the semantic property you intended to change—for
example, a direct destination store and the absence of an unsafe conversion—
rather than copying the entire dump into FileCheck assertions.

## Troubleshooting Dumps

### The directory is empty

1. Confirm the variable is visible to Python:

   ```sh
   python -c 'import os; print(os.environ.get("TRITON_SHARED_DUMP_PATH"))'
   ```

2. Use a fresh `TRITON_CACHE_DIR`.
3. Confirm the selected test actually launches a Triton kernel.
4. Verify the installed backend points to your checkout; see
   [Debugging](04-Debug.md#confirm-that-your-source-changes-are-installed).

### Only some files exist

The next stage probably failed. The last successfully written file narrows the
problem:

- only `tt.mlir`: Triton-RISCV structured conversion failed;
- through `ttshared.mlir`: Buddy vector lowering failed;
- through `vector.mlir`: LLVM-dialect lowering or translation failed;
- through `ll.ir`: object generation, linking, or runtime failed.

### Dumps belong to the wrong kernel

Run a single test in a new process and give it a unique dump directory. Avoid a
full suite when investigating one kernel.
